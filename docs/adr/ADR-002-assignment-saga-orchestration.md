# ADR-002. Оркестрация саги назначения исполнителя

- **Статус:** принято для учебной архитектуры
- **Дата:** 2026-10-29
- **Связи:** FR-04, FR-06, NFR-02, NFR-04, DQ-03, DQ-04, ADR-001

## Контекст

Назначение меняет заявку в контексте «Управление заявками» и резервирует доступность инженера в логически отдельном контексте «Управление загрузкой». Общей ACID-транзакции нет. Возможны timeout после фактического резерва, конкурентное назначение и отказ компенсации. Диспетчеру нужен один наблюдаемый итог, а NFR-04 требует аудит автора и действия.

Уведомление и аналитика не являются частью атомарного успеха: они реагируют на подтверждённый факт асинхронно.

## Рассмотренные варианты

| Критерий | A: синхронная цепочка без саги | B: хореография событий | C: оркестрация в Repair Request Service |
|---|---|---|---|
| Видимость состояния | низкая; timeout не объяснён | распределена по consumers | высокая; одна запись саги |
| Компенсация резерва | ad hoc | событие-компенсация, трудно связать исход | явная команда по `saga_id` |
| Конкурентное назначение | частично | eventual, возможны гонки | optimistic lock + уникальное активное назначение |
| Связанность | высокая синхронная | низкая | оркестратор знает Workforce API |
| Сложность для двух бизнес-участников | низкая в happy path, высокая при сбое | неоправданно высокая трассировка | умеренная и локализованная |
| Наблюдаемость для диспетчера | отдельная доработка | требует сборки распределённой картины | встроенный статус и endpoint |

## Решение

Выбрана **оркестрация в Repair Request Service**.

Оркестратор хранит `saga_id`, текущий шаг, request/engineer ID, reservation ID, число попыток, ошибки и timestamps. На время саги он блокирует конкурирующее назначение, но не меняет пользовательский статус и не отменяет прежнего исполнителя. Workforce вызывается идемпотентно с `saga_id`. Поворотный шаг — локальный commit нового активного назначения, закрытия прежнего назначения при переназначении, статуса, history и outbox. До него новый резерв компенсируется; после него уведомления и аналитика только повторяются.

Сага не выделяется в отдельный универсальный workflow engine: два бизнес-участника и текущая нагрузка этого не оправдывают. Реализация — модуль внутри сервиса заявок с устойчивым состоянием в PostgreSQL.

## Последствия

### Положительные

- диспетчер видит единый статус и может безопасно проверить неизвестный исход;
- порядок, timeout и компенсация заданы в одном месте;
- конкурентные изменения защищены `If-Match` и уникальными ограничениями;
- неуспех уведомления/аналитики не ломает основную операцию.

### Отрицательные

- Repair Request Service знает контракт Workforce и становится владельцем процесса;
- нужны таблица состояния саги, recovery job и ручная очередь разбора;
- компенсация может не выполниться, поэтому всё равно требуется `failed_manual_review`;
- изменение шагов процесса требует изменения оркестратора и его тестов.

## Правила отказа

1. Повтор резервирования и отмены — только с прежним `saga_id`.
2. После timeout сначала GET состояния; максимум 3 проверки с backoff в пределах 60 секунд.
3. Неопределённый исход блокирует новое назначение этой заявки до автоматического или ручного разбора.
4. Компенсация — новое аудируемое действие, она не стирает факт временного резерва.
5. После pivot переназначение — новая команда и новая сага, не технический rollback.

## Проверка

- контрактный тест happy path и отказа `ENGINEER_UNAVAILABLE`;
- сбой после резерва до локального commit приводит к подтверждённой отмене;
- потеря ответа на reserve не создаёт второй резерв;
- сбой после pivot не теряет `RepairRequestAssigned.v1` благодаря Outbox;
- параллельные команды с одним ETag: одна успешна, вторая получает 412/409;
- неуспешная компенсация видна в `failed_manual_review` и не выдаётся за завершённый отказ.

Это план проверок целевого backend; фактическая реализация саги пока отсутствует.

## Триггеры пересмотра

- процесс расширяется до многих независимых участников и оркестратор становится узким местом;
- корпоративная workflow-платформа становится стандартом;
- Workforce оказывается не отдельным владельцем данных, а локальным модулем той же БД — тогда достаточно одной ACID-транзакции и сага не нужна;
- медиана ручных разборов превышает согласованный порог или компенсации систематически не подтверждаются.
