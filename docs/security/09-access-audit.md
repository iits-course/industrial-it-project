# Неделя 9 · Доступ, аутентификация и аудит

Роли взяты из [§6.2 требований](../04-requirements.md). Область диспетчера по участкам, доступ к журналу и сервисные полномочия — проектные правила для согласования. Роль руководителя сохраняет обзор всех заявок; аналитика получает согласованные поля через собственный контур.

## 1. Матрица RBAC + ABAC

## 2. Аутентификация людей и сервисов

- **Люди.** Корпоративный SSO, OIDC Authorization Code с PKCE. Сервис заявок принимает access token для своего API и проверяет подпись, разрешённый алгоритм, `iss`, `aud`, срок и назначение токена. Сопоставление `sub → user_id` и групп с ролями оставлено в `access-audit` по [неделе 8](../08-external-environment.md). Доступ по старым ключам ограничен TTL JWKS и сроком токена. При недоступности SSO новый вход ждёт восстановления. Для критических операций при недоступности подтверждённых атрибутов запись запрещается.
- **Сервисы.** Для Workforce проектируется OAuth 2.0 Client Credentials с отдельным клиентом и раздельными scopes reserve/read/cancel. RabbitMQ и PostgreSQL используют отдельные технические учётные записи с TLS и минимальными ACL. Notification Adapter использует учётные данные провайдера только на своей границе.
- **Секреты.** Учётные данные и ключи хранятся в корпоративном хранилище секретов, выдаются среде отдельно и ротируются. ИБ согласует сроки жизни, процедуру экстренного отзыва и допустимый срок кэша ролей и JWKS. Токены и секреты исключены из диагностики. При компрометации ИБ отзывает клиента или сессии, ротирует соответствующие секреты и сверяет журнал с резервами и событиями по correlation ID.

## 3. Юридически значимые действия и неизменяемость

Для анализа ответственности предлагается фиксировать создание заявки, изменение окончательного приоритета, назначение и переназначение, компенсацию резерва, запись результата, закрытие, изменение полномочий, отказ в доступе и чтение защищённого аудита. Перечень и сроки хранения согласуются с ИБ и владельцем процесса. История карточки остаётся бизнес-представлением изменений.

| Поля | Назначение |
|---|---|
| `audit_event_id`, `occurred_at` | Уникальность и UTC-время сервера |
| `actor_id`, `actor_type`, `effective_role`, `initiator_id` при фоновой операции | Кто действовал и от чьего имени |
| `action`, `target_type`, `target_id`, `org_unit_id` | Действие, объект и область; ID заявки при наличии |
| `source`, `result`, `reason_code`, `policy_version` | Канал, успех или отказ, основание и применённая версия политики |
| `before` / `after` для значимых полей, `correlation_id`, `saga_id` при наличии | Проверка изменения и связь с операцией |

Применяется отдельное append-only хранилище с контролем неизменности на уровне хранилища и отдельным владельцем ИБ. Изменение и удаление штатными учётными записями запрещены. Записи минимизированы: ID и коды вместо контактов, токенов и свободного текста. Успешные изменения фиксируются вместе с буфером доставки, отказы записываются отдельной транзакцией, чтение журнала само аудируется. Детали отказов и повтора доставки закреплены в [ADR-007](../adr/ADR-007-assignment-security.md).
