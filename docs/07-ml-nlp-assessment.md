# Оценка ML/NLP-кандидата v1.0

## 1. Кандидат и решение

**Кандидат:** NLP-подсказка категории неисправности и специализации исполнителя по тексту описания заявки.

**Решение v1:** ML **не внедрять сейчас**. Сначала реализовать объяснимую rule-based подсказку, оставить окончательный выбор человеку и собирать подтверждённую разметку. Пересмотреть ML после накопления данных и доказанного выигрыша над baseline.

NLP не меняет приоритет, не назначает инженера и не закрывает заявку. Это согласуется с FR-04/NFR-04 и не переносит дорогую ошибку на модель.

## 2. Оценка по шести критериям

| Критерий | Оценка кандидата | Вывод |
|---|---|---|
| Цена ошибки | Неверная категория задержит маршрутизацию; автоматическое назначение может отправить неподходящего инженера | только подсказка; подтверждает оператор/диспетчер |
| Данные | Система новая, размеченной истории нет; синтетический прототип не годится для обучения | обучать модель сейчас нельзя |
| Базовое правило | 5–10 групп терминов (`утечка/давление` → гидравлика, `напряжение/автомат` → электрика) дают прозрачный baseline | начать с правил и измерить их качество |
| Объяснимость | Пользователю нужно понять, почему предложена категория | показывать совпавшие признаки; для ML — top factors/ключевые фрагменты, без ложной уверенности |
| Дрейф | Появляются новые модели оборудования, жаргон и виды неисправностей | мониторить долю unknown, confidence и исправления по времени/цехам |
| Эксплуатация | Нет назначенного model owner, pipeline разметки и бюджета мониторинга | ML не готов к промышленной эксплуатации |

## 3. Baseline без ML

Rule engine возвращает `suggested_category`, `suggested_specialty`, список сработавших правил и версию ruleset. Если нет уверенного правила или есть конфликт, поля остаются неподсказанными.

Пример:

```json
{
  "suggested_category": "hydraulics",
  "suggested_specialty": "hydraulics",
  "confidence_band": "high",
  "matched_terms": ["давление", "гидросистема"],
  "ruleset_version": "1.0.0"
}
```

Это не контракт принятия решения. Оператор подтверждает категорию, диспетчер — исполнителя.

## 4. Human-in-the-Loop

```text
Описание заявки
  → правило/модель предлагает категорию + confidence + версию
  → пользователь видит подсказку и основание
  → подтверждает или исправляет
  → только подтверждённое значение записывается в RepairRequest
  → предложение, решение человека и итог ремонта попадают в набор обратной связи
```

| Условие | Действие |
|---|---|
| высокая уверенность | предзаполнить поле, но потребовать явное подтверждение |
| низкая уверенность или конфликт | не предзаполнять; показать возможные варианты |
| компонент недоступен | форма работает без подсказки; ручной выбор обязателен |
| пользователь исправил подсказку | сохранить feedback с версией rules/model, без свободных ПДн |
| критический приоритет | ML не определяет его; применяются согласованные бизнес-правила и решение диспетчера |

## 5. Входные критерии для пилота ML

Пороговые значения — проектные гипотезы для решения go/no-go, а не достигнутые результаты:

1. не менее 5 000 закрытых заявок с подтверждённой категорией и результатом, без синтетических записей;
2. согласованность разметки на контрольной выборке `Cohen's kappa ≥ 0,8`;
3. временное разделение train/validation/test, чтобы исключить утечку из будущего;
4. сравнение с правилами на одной выборке;
5. улучшение `macro-F1` минимум на 0,10 абсолютного значения и отсутствие ухудшения recall редких критичных классов;
6. ручное подтверждение сохраняется, пока цена ошибки и реальное качество не пересмотрены владельцем процесса;
7. назначены Model Owner, Data Steward, график мониторинга и бюджет поддержки.

Если данных меньше, разметка нестабильна или правила дают сопоставимое качество, ML не внедряется.

## 6. Контракт возможного ML-компонента

Если критерии выполнены, компонент оформляется как отдельный заменяемый контейнер:

- вход: `equipment_model`, `org_unit_id`, нормализованный текст без ФИО/контактов;
- выход: список `{category, probability}`, `model_version`, `explanation_tokens`, `request_id` трассировки;
- timeout: ≤ 500 мс в бюджете формы; без автоматического retry пользовательского ввода;
- fallback: rule engine, затем ручной выбор;
- логирование: версия, confidence, принятое/исправленное решение; исходный текст хранится только по политике OLTP;
- отказ компонента не блокирует создание заявки.

## 7. Метрики эксплуатации

| Метрика | Для чего |
|---|---|
| coverage подсказок | понять, как часто компонент вообще помогает |
| acceptance/correction rate | измерить пользу и получить feedback |
| macro-F1 и per-class precision/recall на исправлениях | не скрыть деградацию редких классов средним значением |
| доля low-confidence / unknown | обнаружить новые темы и дрейф |
| распределение текста/оборудования по периодам | data drift |
| p95 latency и error rate | эксплуатационная пригодность |
| время до назначения | доказать бизнес-эффект, а не только ML-метрику |

## 8. Риски

- Исторические назначения отражают прошлую нехватку специалистов и могут закрепить перекосы.
- Свободный текст может случайно содержать ПДн; минимизация и доступ нужны до обучения.
- Accuracy на несбалансированных классах вводит в заблуждение, поэтому используется macro-F1 и per-class metrics.
- Уверенность модели не равна вероятности без калибровки.
- Автоматизация назначения нарушила бы границу ответственности диспетчера; в v1 она запрещена.
