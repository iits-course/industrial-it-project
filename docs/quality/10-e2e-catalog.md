# Неделя 10 · Каталог E2E

Сценарии проектные. Каждый прогон создаёт изолированные данные из [стратегии](10-quality-strategy.md). Проверка связывает интерфейс или API и оракулы по ID заявки, correlation ID, а где уместно — saga ID и event ID. Для ожиданий используются бюджеты из требований и [правил отказа](../08-external-environment.md).

## E2E-01 · Регистрация и безопасная доставка после обрыва

**Ценность:** заявка не теряется и регистрируется один раз. **Связи:** FR-01, NFR-01/02, DQ-01/03/04, A-01.

**Данные и шаги.** Сотрудник входит, выбирает валидное оборудование своего участка, заполняет форму синтетическим описанием и временем обнаружения. АРМ сохраняет операцию и отправляет её. Сотрудник открывает подтверждённую карточку.

**Оракулы.** У АРМ есть подтверждённый ID, в OLTP одна заявка с коррелирующей записью истории и outbox, опубликовано `RepairRequestCreated.v1` с валидным payload, в истории и защищённом аудите записан инициатор. KPI регистрации сравнивает время обнаружения и серверное время регистрации на штатной ветке.

| Ветка | Инъекция и ожидаемый результат |
|---|---|
| Обрыв до запроса | Перезапустить АРМ в окне автономности до 4 ч; очередь и ID сохраняются, до отправки записей в OLTP нет; после восстановления за ≤ 60 с очередь подтверждается и появляется одна заявка |
| Потеря ответа после commit | Повтор с тем же ключом и телом возвращает сохранённый 201; ни второй заявки, ни нового факта регистрации |
| Изменённое тело при том же ключе | API возвращает 409; сохранённая заявка и outbox без изменений |
| Неизвестное оборудование | Создание отклоняется, нет записи заявки и события; АРМ показывает ошибку, требующую исправления |
| Задержка EAM | Ответ через 15 с превышает таймаут адаптера 10 с; `sync_failed` виден владельцу, при ещё допустимой проекции форма и регистрация работают локально |

Для двух веток обрыва и остальных сценариев QA-02, перечисленных в карточке Spike, промышленный прогон закрепляет 50 повторов каждого сценария и проверяет проектные пороги NFR-02.

## E2E-02 · Назначение с резервом Workforce

**Ценность:** диспетчер получает единственный подтверждённый результат. **Связи:** FR-04, NFR-04, DQ-04, T-02/03/05/06/10, A-03/04/08.

**Данные и шаги.** Есть новая заявка, диспетчер её области и доступный инженер. Диспетчер читает карточку и ETag, отправляет назначение с ключом и причиной. При 202 читает состояние по Location до терминального исхода согласно контракту.

**Оракулы.** Workforce хранит ровно один резерв для saga ID; в OLTP единственное активное назначение и статус `assigned`; история, защищённый аудит и outbox связаны с операцией; брокер получает `RepairRequestAssigned.v1`.

| Ветка | Инъекция и ожидаемый результат |
|---|---|
| Отказ Workforce | `ENGINEER_UNAVAILABLE`; новое назначение и событие отсутствуют, заявка сохраняет прежнее состояние |
| Резерв записан, ответ задержан на 15 с | Через 2 с оркестратор переходит к сверке по saga ID; при подтверждении резерва доводит назначение без нового резерва |
| Отказ до pivot и сбой компенсации | Если отмена не подтверждена в рамках политики саги, наблюдается `failed_manual_review` и блокировка новых назначений; действующее назначение сохраняется, события нового назначения нет, попытка компенсировать аудируема |
| Одновременные команды | Один подтверждённый результат, конкурент получает 409/412, один активный исполнитель |
| Операция вне области или роли | 403, отказ в аудите, изменений, резерва и события нет; чтение саги и выдача результата повтора требуют актуальных прав |

## E2E-03 · Доставка результата назначения потребителям

**Ценность:** участники узнают о назначении, аналитика отражает подтверждённый факт. **Связи:** FR-03/04, DQ-04/05/06, T-07/08/09, A-09/10, ADR-004/005.

**Данные и шаги.** На stage назначить инженера по E2E-02. По ID события проследить relay, RabbitMQ, обработчик уведомлений, адаптер и загрузчик витрины.

**Оракулы.** В OLTP назначение действительно; outbox доставлен, у каждого потребителя одна обработка, у провайдера одна доставка, в витрине одна актуальная версия назначения, расхождение исчезает в пределах DQ-05, факт доставки и lag наблюдаемы.

| Ветка | Инъекция и ожидаемый результат |
|---|---|
| Брокер недоступен на момент commit | Назначение видно в АРМ, outbox остаётся устойчивым; после восстановления публикация и доставка догоняют с тем же event ID |
| Повтор сообщения | Повторная доставка не меняет витрину второй раз и не дублирует уведомление |
| Провайдер отвечает через 15 с | Через 5 с статус `unknown`; lookup по event ID, повтор только с тем же ключом по политике; при исчерпании попыток запись в DLQ, назначение и аналитика действуют |
| Analytics Loader остановлен | Витрина помечена как неполная на лаге; уведомление доставлено независимо; после запуска сверка идёт по версии агрегата и контрольному окну |

## E2E-04 · Ремонт и закрытие с результатом

**Ценность:** история обслуживания содержит подтверждённый результат и автора. **Связи:** FR-03/05/06/07, NFR-04, DQ-02/05, A-02/05/06/07.

**Данные и шаги.** На назначенной заявке диспетчер утверждает приоритет с причиной, назначенный инженер начинает работу, записывает диагностику и результат, отмечает выполнение. Диспетчер закрывает заявку. При чтении сотрудник видит итог своей заявки. Шаги закрытия и смены статусов опираются на FR, пока их API не формализован.

**Оракулы.** В OLTP сохранены результат, переходы и время закрытия; карточка и история отражают итог; в аудите есть акторы и результаты действий; outbox и потребители отражают факт выполнения по `RepairRequestCompleted.v1`, аналитика видит версию выполнения. Закрытие проверяется в OLTP, карточке и аудите. Событие закрытия отсутствует в текущем AsyncAPI.

| Ветка | Инъекция и ожидаемый результат |
|---|---|
| Чужой инженер сохраняет результат | Нет изменения карточки и истории, отказ записан в аудите |
| Завершение без диагностики или результата | Переход отклонён, статус остаётся «В работе», события выполнения нет |
| Преждевременное закрытие | Диспетчер не может закрыть заявку до состояния «Выполнена»; версия и outbox без изменений |
| Оператор меняет окончательный приоритет | Отказ в API и запись в аудите; окончательное значение сохранено |
