# Неделя 10 · Стратегия качества РемКонтура

Основание — занятие 10, слайды 6–12 и 21–35, [FR/NFR](../04-requirements.md), [контракты](../07-contract-versioning.md), [модель угроз](../security/09-threat-model.md) и [матрица доступа](../security/09-access-audit.md). Приоритетные риски — потеря заявки при обрыве, неверное назначение, незаметная задержка потребителей и нарушение доступа.

## 1. Уровни проверок

| Уровень | Объект проверки | Пример для РемКонтура |
|---|---|---|
| Модульный, самый многочисленный | Правила домена, политики и классификация ошибок | Переходы статусов, обязательность результата, область диспетчера, нормализация ответа провайдера |
| Компонентный | Сервис через API с управляемыми зависимостями | 403 вне области и отсутствие записи в домене; 409 при изменённом теле с прежним ключом |
| Контрактный | Форматы и совместимость поставщика с потребителями | OpenAPI заявок и Workforce, AsyncAPI и примеры событий; ожидания потребителей проверяются в сборке поставщика |
| Интеграционный | Реальные PostgreSQL и RabbitMQ в изолированной среде | Атомарность commit и outbox, повтор после потери подтверждения, inbox, защищённый аудит |
| E2E, четыре сценария | Бизнес-результат через клиент/API, хранилища, события и потребителей | [Каталог E2E](10-e2e-catalog.md) |

Проверка ставится на самый низкий уровень, на котором наблюдается риск. Основной объём приходится на модульные проверки, контрактные и интеграционные подтверждают границы, компонентные проверяют сервис целиком, E2E покрывает четыре бизнес-цепочки. Нагрузка и сбои проверяются отдельно на соответствующих средах.

## 2. Среды и ворота качества

| Ворота | Среда и данные | Условие прохождения |
|---|---|---|
| Локальный запуск | Модульные и компонентные проверки, синтетические наборы, заглушки | Быстрая обратная связь по изменению |
| Pull request | Эфемерная среда PR, модульные и контрактные проверки | Все проверки зелёные; несовместимый контракт блокирует слияние; рабочая цель прогона ≤ 10 мин |
| Сборка | Изолированные PostgreSQL, RabbitMQ и эмуляторы | Компонентные и интеграционные проверки зелёные; артефакт продвигается по средам без пересборки |
| Stage | Все сервисы, независимые наборы тестов, управляемые сбои и доступные песочницы | Все негативные ветки каталога и матрица доступа проходят, оракулы подтверждены в данных |
| Предпрод | Конфигурация, близкая к целевой, синтетическая нагрузка | QA-03 измерен для списка, карточки и формы на профиле §6.5; p95 каждой ≤ 2 с по рабочей гипотезе |
| Продуктив | Безопасный smoke после выкатки, чтение состояния и телеметрия | Smoke проходит, отклонения метрик из матрицы передаются владельцам |

Сохраняются результаты прогонов, версии контрактов и идентификатор сборки. Случайное падение фиксируется как дефект с владельцем, тест можно изолировать до исправления. Динамика доли покрытых NFR, угроз и ячеек доступа, длительности PR, случайных падений и дефектов после релиза оценивается по отчётам прогонов и реестру дефектов.

## 3. Синтетические данные и эмуляторы

Генератор проектируется как фабрики с фиксированным seed. На каждый прогон выделяется отдельное пространство данных, на сценарий — набор ID пользователей, участков, оборудования, заявок и correlation ID. Базовый набор: два участка, оборудование каждого участка, сотрудник, диспетчер первой области, инженер с подходящим допуском и второй инженер без доступного резерва. Время генерации задаётся управляемыми часами в UTC. Описание и результат ремонта берутся из шаблонов, контакты направляются в тестовый приёмник. Реальные ПДн, секреты и выгрузки производственной базы не используются. Для нагрузки генератор создаёт 50 000 заявок с согласованными ссылками и статусами, профиль запуска — до 50 сессий, 20 чтений и 5 изменений в секунду по [§6.5](../04-requirements.md).

| Зависимость | Поведение эмулятора для проверки | Проверка совместимости |
|---|---|---|
| Workforce | Успех, отказ инженера, сохранённый резерв с потерянным ответом, задержка 15 с, отказ отмены; отдельное состояние по saga ID | Контракт OpenAPI и проверки против тестового поставщика при доступности |
| EAM/HR | Известная и отсутствующая запись, задержка 15 с, отказ; фиксированная версия справочника | Синтетические контрактные ответы адаптеров и песочница при наличии |
| Уведомления | Успех, задержка 15 с, временная/постоянная ошибка, lookup отправки по event ID | Песочница провайдера или согласованные образцы ответа |
| SSO | Тестовые роли и области, истечение токена, смена ключа, недоступность JWKS | Тестовый tenant корпоративного SSO |
| АРМ и брокер | Обрыв связи, недоступность брокера и повтор доставки | Тестовое управление сетью и реальный RabbitMQ в изолированной среде |

Двойники реализуются за интерфейсами адаптеров. Запуск имитации доступен только тестовым средам. Управляемые часы ускоряют проверки истечения; реальное время и нагрузка проверяются отдельно. Асинхронные оракулы ждут условия с ограниченным сроком и фильтром по correlation ID, без фиксированных пауз. После сценария среда уничтожается либо данные очищаются по ID прогона. Решение о наборах и изоляции зафиксировано в [ADR-008](../adr/ADR-008-synthetic-test-data.md).
